# ReFlux: exit-ноды на своём сервере

ReFlux запускает на одном Linux-сервере с Docker по отдельной exit-ноде OpenFlux
на каждого клиента. Трафик клиентов выходит в интернет только через
AmneziaWG-туннели и никогда не уходит с адреса самого сервера.

```
клиент ──документ mail.ru──▶ [reflux-node-<имя>] ─┐  общая сеть
клиент ──документ mail.ru──▶ [reflux-node-<имя>] ─┤
                                                   ▼
                       [reflux-egress: kill switch, DNS-over-TLS]
                          ├─ awg-ru    российские адреса (и mail.ru)
                          └─ awg-world всё остальное, с резервными серверами
```

- **Один клиент — один канал:** свой документ, свой ключ, свой контейнер.
  Нода обслуживает одного активного клиента, поэтому документ нельзя делить.
- **Ноды** работают в режиме `l4` без привилегий, файловая система только для
  чтения, портов наружу не открывают. Своей сети у них нет: они в сети egress.
- **Egress** держит два туннеля: `ru-1.conf` для российских адресов (список
  сетей из статистики RIPE, обновляется раз в сутки) и `world-N.conf` для
  остального. Вместо российского туннеля можно выпускать Россию напрямую
  через провайдера сервера (см. «Россия напрямую»). Если мировой туннель не отвечает 30 секунд, egress переходит на
  следующий `world-N.conf` и не возвращается на прежний сам. Если упал
  российский туннель, российский трафик стоит до его восстановления.
- **Kill switch:** из контейнера наружу выпускается только UDP к серверам
  AmneziaWG. Нет туннеля — нет трафика.
- **DNS:** `unbound` в egress, проверка DNSSEC, запросы к Quad9 и Cloudflare
  по TLS через мировой туннель. Домены транспортов (`mail.ru`,
  `datacloudmail.ru`, `yandex.ru`, `yandex.net`) спрашиваются у DNS Яндекса
  через российский туннель: документ mail.ru продолжает работать, даже когда
  мировой туннель лежит.

## Установка

Одной командой, от пользователя, который будет управлять ReFlux (не от root):

```sh
curl -fsSL https://github.com/BeleBob/ReFlux/releases/latest/download/install.sh | sh
```

Скрипт скачивает `reflux` последнего релиза в `~/.local/bin`, сверяет его с
`SHA256SUMS` и запускает мастер `reflux setup`. Конкретная версия:
`REFLUX_VERSION=1.0.0`; только установить, без мастера: `REFLUX_NO_SETUP=1`
(обе переменные — перед `sh`: `… | REFLUX_NO_SETUP=1 sh`).

Мастер проходит шаги по порядку. Каждый шаг сначала проверяет и меняет только
то, чего не хватает; всё, что требует `sudo`, он сначала спрашивает. Если нужно
действие владельца (перезайти после добавления в группу `docker`, поставить
модуль ядра), мастер останавливается — повторный `reflux setup` продолжит с
того же места. `reflux setup --check` только показывает, чего не хватает.

1. Docker с плагином compose (предлагает официальный скрипт get.docker.com) и
   доступ к нему без `sudo`.
2. Модуль ядра `amneziawg`: загрузить сейчас и при каждой загрузке; если модуля
   нет — ссылка на инструкцию по установке.
3. `loginctl enable-linger`: бот и сайт работают без входа пользователя.
4. Правило маршрутизации в обход VPN самого сервера — только если такой VPN
   есть (ниже, «Вручную», п. 1).
5. Конфиги AmneziaWG: мастер спрашивает пути к файлам, проверяет их и кладёт в
   `~/reflux/egress/` с правами `600`. Без российского конфига Россия идёт
   напрямую с адреса сервера — только после явного согласия.
6. `reflux heal` в cron раз в минуту.
7. Запуск egress (`reflux apply`) и ожидание туннелей.
8. По желанию: Telegram-бот, бот для клиентов, сайт в домашней сети,
   ежедневные копии, первый клиент.
9. Итоговая проверка `reflux doctor`.

### Вручную

То же без мастера. Нужны Docker с плагином compose и модуль ядра `amneziawg`
на хосте (пакет `amneziawg-dkms`). Проверка: `grep amneziawg /proc/modules`.

1. **Правило маршрутизации.** Если трафик самого сервера идёт через свой VPN
   (у нас `awg0`), туннели egress должны идти мимо него:
   ```sh
   sudo cp deploy/reflux/host/reflux-egress-route.service /etc/systemd/system/
   sudo systemctl daemon-reload
   sudo systemctl enable --now reflux-egress-route
   ip rule   # первой после 0: строка 100: from 172.31.250.0/24 lookup main
   ```
   Без этого правила `reflux apply` откажется запускать egress.

2. **Утилита `reflux`** из релиза `reflux-v*` (проверьте сумму по `SHA256SUMS`):
   ```sh
   install -m 0755 reflux-linux-amd64 ~/.local/bin/reflux
   ```

3. **Конфиги AmneziaWG** в `~/reflux/egress/` с правами `600`:
   - `ru-1.conf` — сервер в России;
   - `world-1.conf`, `world-2.conf`, … — остальной мир, в порядке переключения.

   Каждый конфиг должен быть выдан только для этого сервера: один ключ
   AmneziaWG не работает на двух устройствах сразу. Одновременно открыты ровно
   два подключения: российское и одно мировое.

4. **Запуск egress** и проверка:
   ```sh
   reflux apply
   reflux status
   ```
   В выводе `status` обе строки `world` и `russia` должны быть `up`.

## Версии и релизы

`reflux version` показывает версию утилиты, коммит и образы, которые она
использует. Релизы публикуются на GitHub как `reflux-vX.Y.Z`: в них
`reflux-linux-amd64`, `reflux-linux-arm64`, установщик и `SHA256SUMS`, а
описание — из [CHANGELOG](CHANGELOG.md). Утилита из релиза по умолчанию
берёт образы `:latest` (образы последнего релиза), сборка из ветки `main` —
образы `:main`; переопределить можно `REFLUX_NODE_IMAGE` и
`REFLUX_EGRESS_IMAGE`.

Выпуск релиза: перенесите в `docs/reflux/CHANGELOG.md` всё из «Не выпущено» в
раздел `## [X.Y.Z] - дата`, слейте в `main` и поставьте тег:

```sh
git tag reflux-vX.Y.Z && git push origin reflux-vX.Y.Z
```

GitHub соберёт утилиту и образы (`X.Y.Z` и `latest`) и опубликует релиз.

## Вход в mail.ru

С 15 октября 2026 года mail.ru открывает документы только вошедшим
пользователям. Без входа ноды не подключаются к документам: doctor пишет
«у нод нет аккаунта для входа». Все ноды входят под одним аккаунтом
владельца, а клиенты — каждый под своим в приложении: при подключении ReFlux
попросит войти в mail.ru.

Как дать нодам вход:
1. Откройте приватное окно Firefox и войдите на cloud.mail.ru. Это отдельная
   сессия: обычный браузер она не затронет.
2. F12 → «Сеть» → обновите страницу → любой запрос к cloud.mail.ru → «Куки» →
   правый клик → «Копировать всё». Или Cookie-Editor → Export → Header String.
   В приватном окне дополнения работают, только если им это разрешено
   (`about:addons` → дополнение → «Запуск в приватных окнах»).
3. `reflux mailru login`, вставьте, Ctrl+D. Или на сайте: «mail.ru» →
   «Новые cookies».
4. Закройте окно, не нажимая «Выйти»: выход завершит сессию, под которой
   работают ноды.

```sh
reflux mailru                # под каким аккаунтом ноды, когда проверен вход
reflux mailru login [файл]   # новые cookies: из файла или вставить, Ctrl+D
reflux mailru check          # проверить вход сейчас
```

reflux проверяет cookies из egress (mail.ru видит тот же адрес, что и у нод) и
хранит их в `~/reflux/mailru/cookies` (600). Каталог подключён к нодам только
для чтения. Нода перечитывает файл, когда mail.ru отказывает ей во входе,
поэтому новые cookies доходят до нод без перезапуска. Обновление до версии с
этим входом один раз пересоздаёт ноды: в `node.conf` появляется
`MailruCookiesFile`.

Бот проверяет вход каждые 15 минут вместе с документами и сообщит, если mail.ru
перестанет его принимать; тогда дайте новые cookies. Cookies — это вход в
почту. Не присылайте их в Telegram: бот их не принимает, а на сервере они
попадают только в резервные копии. В документах аккаунт виден под своим именем,
и если mail.ru заблокирует его за туннель, пострадает и его почта.

## Клиенты

```sh
reflux add phone --transport mailru --url https://cloud.mail.ru/public/XXXX/YYYY
reflux list
reflux show phone            # данные для клиента ещё раз
reflux pause phone           # временно отключить (ключ и документ сохраняются)
reflux resume phone          # включить обратно
reflux expire phone 30d      # доступ на 30 дней (или 2w, 12h, 2026-12-31, never)
reflux revoke phone          # остановить ноду и удалить ключ
reflux logs phone | reflux logs egress
```

На каждого клиента нужен **новый** документ mail.ru, открытый по ссылке.
Ссылки с символами `#`, `;` и пробелами не принимаются: `.conf` ядра их обрезает.

`add` и `show` печатают:
- поля для ручного ввода (транспорт, ссылка на документ, ключ шифрования,
  Legacy codec выключен): для приложений без импорта ссылок, например
  damnurmum/OpenFlux-Android;
- ссылку `reflux://` и QR-код: для ReFlux для Android 1.1.1 и новее (ссылка —
  та же `openflux://` со своей схемой; другим приложениям OpenFlux — поля для
  ручного ввода).

`list` (и `status`) показывает по каждому клиенту:

```
NAME   TRANSPORT  ACCESS             NODE         CLIENT  DOWN    UP
phone  mailru     active             Up 16 hours  online  1.4 GB  52 MB
guest  mailru     until 2026-10-30…  Up 2 days    offline 80 MB   3 MB
```

- `ACCESS` — `active`, `paused`, `until <дата>` или `expired`;
- `NODE` — состояние контейнера ноды;
- `CLIENT` — подключён ли клиент к каналу сейчас (`online`) или нет
  (`offline`; клиент выключен или нет связи);
- `DOWN`/`UP` — трафик канала к клиенту и от клиента с запуска ноды.

Данные берутся у самой ноды через её IPC-сокет (`~/reflux/state/<имя>/ipc.sock`).
`-` в этих столбцах: нода остановлена или ещё запускается.

### Пауза и срок доступа

`pause` останавливает ноду клиента, но оставляет ключ, документ и cookies:
`resume` включает его с той же ссылкой, выдавать данные заново не нужно.

Срок доступа задаётся при добавлении (`add ... --expires 30d`) или потом
(`expire <имя> <срок>`). Срок — `never`, дата (доступ действует весь этот день
по времени сервера), число дней или недель (`30d`, `2w`) или часы (`12h`).
Когда срок вышел, `reflux heal` из cron в течение минуты останавливает ноду.
Продлить: `expire <имя> 30d` — нода запустится снова; `resume` просроченного
клиента не включает.

Ссылка и ключ дают доступ к каналу: передавайте их только его владельцу.
`revoke` удаляет ключ навсегда; запись о канале остаётся в `~/reflux/revoked/`.

### Несколько документов на клиента

Клиенту можно дать до пяти документов, все равноправны (одинаковый
приоритет, 100). Нода работает со всеми сразу: каждое новое соединение
клиента идёт через документ, где меньше всего ждёт отправки и меньше активных
соединений, и остаётся на нём, пока активно, чтобы не перемешивались пакеты.
Документ, который отказал или заблокирован, просто выпадает: его соединения
переходят на остальные, а когда он вернётся, на него снова пойдут новые.
Так распределяет нода то, что идёт к клиенту; от клиента — приложение.
С 14 октября mail.ru пропускает через одно соединение с документом около
9 КБ/с, поэтому несколько документов — это и **скорость**: страница из
нескольких соединений грузится через все документы сразу. Одна загрузка
(одно соединение) по-прежнему идёт через один документ.

```sh
reflux pool                          # пул документов: свободные и занятые
reflux pool add <ссылка>...          # добавить подготовленные документы в пул
reflux docs phone                    # документы клиента: доходит ли каждый, трафик, соединения
reflux docs phone add pool           # ещё один документ из пула
reflux docs phone add <ссылка>       # или конкретный (тип — по ссылке)
reflux docs phone remove 2           # убрать документ 2
```

То же в боте (карточка клиента → «📄 Документы»: «Из пула», «По ссылке»,
«🗑 N» с подтверждением; команда `/docs <имя>`) и на сайте (страница клиента,
блок «Документы»).

- **Режим Session.** С несколькими документами нода становится Session-exit:
  она принимает только приложения в режиме Session. После добавления документа
  обновите профиль в приложении по новой ссылке (`reflux show`, «📱 Показать
  QR»): в ссылке все документы, их порядок и контекст шифрования. Когда снова
  остаётся один документ, нода опять обычная и принимает любые приложения.
- **Ключ не меняется.** Контекст шифрования — первый документ клиента, и он
  сохраняется, даже если первый документ убрать: его место занимает
  следующий (`context` в `client.json`), а профиль в приложении продолжает
  работать через оставшиеся документы.
- **Пул** — `~/reflux/docs-pool.txt` (`0600`): по документу в строке, `тип
  ссылка` или просто `ссылка`, строки с `#` — комментарии. Из пула берётся
  первый свободный документ того же типа, что основной (документы Яндекса
  упираются в SmartCaptcha), потом любой. Один документ — один канал:
  документ другого клиента не принимается.
- **Карантин.** Документ, снятый с клиента (`reflux docs … remove`, кнопка
  «🗑», отзыв клиента), сутки лежит в пуле на карантине и только потом
  выдаётся другому: старое приложение какое-то время ещё стучится в него.
- **Мёртвые документы.** Каждые 15 минут бот проверяет все документы
  клиентов и свободные документы пула. Проверка идёт из контейнера egress,
  поэтому mail.ru видит адрес нод, а не сервера. Если mail.ru дважды подряд
  отвечает, что документ или аккаунт владельца удалён, снят с публикации или
  заблокирован (или ссылка открывает документ только на просмотр), документ
  попадает в список мёртвых. Таймауты, перегрузка и прочие сбои mail.ru
  смертью не считаются: такой документ просто проверят в следующий раз.
  Кроме кругов раз в 15 минут есть быстрая проверка: нода каждую минуту
  сообщает, к каким документам подключена, и документ, который она не держит
  3 минуты, бот проверяет сразу и потом раз в минуту. Заблокированный
  документ так меняется минут за 5, пока второй документ клиента ещё
  работает, и приложение получает новую ссылку через него само. Клиент тут же получает свободный документ из
  пула, нода перезапускается, а бот для клиентов присылает человеку новую
  ссылку и QR. Если свободных нет, мёртвый документ просто убирается, а
  единственный остаётся. Бот пишет, что случилось. Список
  мёртвых — в боте («📄 Документы» на главном экране, кнопки «🔄 N»,
  «🔄 Проверить все мёртвые», «🔎 Проверить все документы сейчас») и в
  консоли:
  ```sh
  reflux pool                  # пул: свободные, занятые, на карантине, мёртвые
  reflux pool check            # проверить и заменить мёртвые сейчас
  reflux pool recheck [<url>]  # проверить мёртвые снова; ожившие — в пул через сутки
  ```
  Мёртвые документы бот сам проверяет снова раз в 12 часов: ожившие через
  сутки карантина возвращаются в пул, о них приходит сообщение.
  Проверка умеет только документы mail.ru. Состояния хранятся в
  `~/reflux/docs-state.json`.
- **Три документа — каждому.** При той же проверке клиент с одним
  документом получает из пула второй, проверенный, а со вторым — третий,
  если в пуле после этого останется хотя бы два свободных (запас на замену
  мёртвых и для новых клиентов). За одну проверку — один документ. Нода
  переходит в режим Session, поэтому бот для клиентов один раз присылает
  новую ссылку.
- **Самообновление.** Нода сама сообщает приложению текущую ссылку клиента
  (`clients/<имя>/offer`, сообщение ядра `ConfigOffer`) при каждом
  подключении и после каждого изменения. Когда документ умирает и заменяется,
  новая конфигурация доходит до приложения через оставшийся рабочий документ,
  и приложение применяет её само. Умеет это ReFlux для Android; другим
  приложениям новую ссылку по-прежнему присылает бот для клиентов. Если
  умерли сразу все документы клиента, остаётся только бот.
- **Состояние документов.** `reflux docs`, экран «📄 Документы» в боте и
  панель показывают по каждому документу: «работает» (клиент слышен через
  него, по нему идёт трафик), «не доходит до клиента», «ждёт клиента»
  (клиент не в сети) или «нет связи с документом» (нода к нему не
  подключена), и трафик через него с запуска ноды. Если клиент в сети, а
  какой-то документ до него не доходит, `reflux doctor`, экран проверок в
  боте, карточка клиента и панель пишут «до клиента не доходят документы N»:
  документ мёртв или в приложении старая ссылка без него. В Telegram бот об
  этом не пишет: документ выпадает и возвращается при коротких сбоях по
  нескольку раз в день, а о мёртвом документе приходит отдельное сообщение.
  Пока телефон не в сети, состояние не меняется.

### Комнаты cups.online

Рядом с документами mail.ru каждый активный клиент получает быстрый канал —
4 комнаты cups.online (сервис собеседований с общим редактором). Каждая
комната — отдельная полоса, вместе они дают ~150–200 КБ/с против ~10 КБ/с у
документа mail.ru. Комнаты получают приоритет 100, документы рядом с ними — 50:
весь трафик идёт через комнаты, а документы ждут в резерве. Если комнаты
закрылись или cups.online недоступен, канал продолжает работать через mail.ru,
и по нему же приложение получает новые комнаты (ConfigOffer). DNS тоже идёт
через комнаты, пока они работают. Клиенту с комнатами хватает двух документов
mail.ru: третий проверка документов ему не выдаёт.

```sh
reflux cups                  # включены ли комнаты, у кого сколько
reflux cups add belebob      # новые комнаты клиенту сейчас (старые заменятся)
reflux cups remove belebob   # убрать комнаты у клиента насовсем
reflux cups off              # не выдавать комнаты (выданные остаются); on — обратно
```

- **Откуда комнаты.** Их создаёт egress (`reflux-egress create-rooms`) с того же
  адреса, с которого работают ноды; список комнат записывается в документы
  клиента (транспорт `cupsonline`) и попадает в ссылку. Ключ шифрования не
  меняется: контекст канала — первый документ mail.ru.
- **Когда выдаются.** При проверке документов (каждые 15 минут) комнаты получает
  один клиент без комнат: cups.online отказывает, если создавать комнаты
  слишком часто. Потом нода перезапускается, приложение получает новую
  настройку по каналу само, а бот для клиентов один раз присылает новую ссылку.
  Кнопка «⚡ Комнаты cups.online» на экране «📄 Документы» выдаёт их сразу.
  Выключатель — в настройках бота.
- **Закрытые комнаты.** Та же проверка открывает страницы комнат. Если
  cups.online дважды подряд ответил, что какой-то комнаты больше нет, клиент
  получает новые комнаты на её место. В список мёртвых и в пул комнаты не
  попадают. Приложение получает новые комнаты через mail.ru само, бот клиенту
  ничего не пишет. Если cups.online не дал новых комнат, старые убираются, и
  канал работает через mail.ru до следующей удачной попытки.
- **Если cups.online не даёт комнаты,** следующая попытка — через час;
  `reflux doctor` и бот пишут «cups.online не даёт комнаты с …».
- **Убранные вручную** комнаты (кнопкой на экране документов или
  `reflux cups remove`) сами не возвращаются: только через `reflux cups add`
  или кнопку.
- **Приложение** должно быть ReFlux для Android 1.4.0 или новее: старые версии
  не читают список комнат нового формата и работают только через mail.ru.
- Хост `interview.cups.online` входит в «каналы напрямую»
  (`~/reflux/egress/carrier-direct`): через российский туннель комнаты
  работали заметно медленнее.

## Шлюз: выбор мирового сервера и режима России

```sh
reflux gateway                     # мировые серверы (* — используется), режим России
reflux gateway world-5.conf        # перейти на world-5 (egress переключится за 10 секунд)
reflux gateway auto                # отменить выбор: egress держит работающий сервер
reflux gateway russia fallback     # Россия: туннель, при сбое напрямую (или tunnel, direct)
reflux gateway carrier direct      # канал mail.ru мимо российского туннеля (или tunnel)
```

Выбор мирового сервера записывается в `~/reflux/egress/world-select` и
сохраняется при перезапуске egress. Если выбранный сервер перестаёт отвечать,
egress как обычно переходит к следующему по порядку и не возвращается к
выбранному сам: выберите его снова, когда он заработает. Смена режима России
перезапускает egress и ноды (как `reflux restart`). То же — кнопкой
«🌐 Шлюз» в боте.

## Канал mail.ru напрямую

```sh
reflux gateway carrier direct      # или tunnel, чтобы вернуть через российский туннель
```

Трафик самих каналов (ноды ↔ документы mail.ru и комнаты cups.online) идёт
мимо российского туннеля, через провайдера сервера; остальные российские
адреса — как настроено режимом России. Egress раз в минуту узнаёт адреса
`cloud.mail.ru`, `docs.datacloudmail.ru` и `interview.cups.online` у своего
DNS, открывает их в kill switch (набор `carrier4`) и направляет в `eth0`;
адрес, который сутки не встречался, возвращается в туннели. Пока адрес не
известен, канал идёт через туннель, как раньше. Другие хосты можно перечислить
в `~/reflux/egress/carrier-direct` по одному в строке (пустой файл — эти три
хоста). Включение и выключение перезапускают egress и ноды.

Зачем: на каждый мегабайт, который скачивает клиент, нода отправляет в
документ около 1,5 МБ, и всё это шло через российский туннель (~26–40 Мбит/с) —
общий для всех клиентов. Цена: mail.ru видит домашний IP сервера; сайты,
которые открывают клиенты, его не видят.

## Россия: туннель с резервом напрямую

```sh
touch ~/reflux/egress/ru-fallback-direct && chmod 600 ~/reflux/egress/ru-fallback-direct
reflux restart
```

Российские адреса идут через `ru-1.conf`. Если туннель не отвечает 30 секунд
(три проверки подряд), egress выпускает их через провайдера сервера, как в
режиме «напрямую»: kill switch открывает российские префиксы до того, как на
них переключаются маршруты. Туннель проверяется и дальше; когда он отвечает
5 минут подряд, Россия возвращается в него, а kill switch снова закрывает
префиксы. Каждое переключение рвёт открытые соединения с российскими адресами
(и с документом mail.ru — нода переподключается сама), поэтому возврат не
мгновенный.

`reflux status`, `doctor` и бот показывают «напрямую (резерв)», пока туннель
не работает; бот присылает уведомление при уходе на резерв и при возврате.

## Россия напрямую

```sh
touch ~/reflux/egress/ru-direct && chmod 600 ~/reflux/egress/ru-direct
reflux restart
```

Только напрямую, без туннеля (файл `ru-direct` важнее `ru-fallback-direct`):
российские адреса (и документ-транспорт mail.ru) уходят через провайдера
сервера, без туннеля; `ru-1.conf` не нужен, у провайдера AmneziaWG занято одно
подключение. Kill switch выпускает мимо туннеля только российские префиксы.
Цена: российские сайты и mail.ru видят домашний IP сервера. Выигрыш на нашем
сервере: канал через mail.ru с ~0,05 до ~3 МБ/с, потому что российский
AWG-сервер давал ~1 Мбит/с. Вернуть туннель: удалить файл и `reflux restart`.

## Обслуживание

`reflux doctor` проверяет всё, от чего зависит работа каналов: модуль
`amneziawg`, правило маршрутизации, конфиги egress, Docker и образы, туннели,
каждую ноду (запущена, в сети egress, есть ли клиент, не теряет ли документ),
cron, место на диске и свежесть резервной копии. Каждая строка — `ok`, `warn` или `FAIL` с подсказкой,
что сделать. Код выхода ненулевой, если есть `FAIL`. Запускайте после
перезагрузки, обновления системы или когда что-то не работает.

| Команда | Что делает |
|---|---|
| `reflux doctor` | проверка сервера и всех нод с подсказками |
| `reflux speedtest` | скорость выхода через egress: Россия и мир |
| `reflux gateway [...]` | мировой сервер и режим России (см. «Шлюз») |
| `reflux rename <имя> <новое-имя>` | переименовать клиента (ссылка и ключ те же) |
| `reflux bot setup/install/test` | Telegram-бот: уведомления и команды (см. ниже) |
| `reflux web install/login` | сайт в домашней сети (см. «Сайт в домашней сети») |
| `reflux update` | скачивает новые образы, перезапускает изменившиеся контейнеры и удаляет старые образы ReFlux |
| `reflux restart` | пересоздаёт egress и все ноды |
| `reflux restart <имя>` | пересоздаёт ноду одного клиента (канал пропадает примерно на 40 секунд) |
| `reflux heal` | останавливает ноды с истёкшим сроком; пересоздаёт ноды, оставшиеся без сети после перезапуска egress |
| `reflux apply --dry-run` | только переписывает `~/reflux/compose.yml` и `node.conf` клиентов |
| `reflux backup [list]` | резервная копия `~/reflux` сейчас / список копий (см. «Резервные копии») |
| `reflux restore <копия>` | вернуть копию и пересоздать egress и ноды |

Если новая версия `reflux` меняет `node.conf` (он создаётся из `client.json`),
`apply` и `update` пересоздают ноды, запущенные со старым конфигом.

Если контейнер egress перезапустился (сбой, обновление Docker), ноды остаются в
его старой сети, где нет выхода наружу. `reflux heal` находит такие ноды и
пересоздаёт только их; поставьте его в cron пользователя (`crontab -e`):

```
* * * * * $HOME/.local/bin/reflux heal >> $HOME/reflux/heal.log 2>&1
```

После перезапуска ноды (`reflux restart`, `update`, `heal`, даже аварийного)
подключённый клиент восстанавливается сам примерно за 40 секунд: нода сразу
входит в документ, клиент через 30 секунд тишины заново проводит рукопожатие.
Проверено и с клиентом на неисправленном ядре OpenFlux (43 с): достаточно, что
исправление есть в ноде. Без него нода и клиент выбивали друг друга из
документа каждые ~30 секунд, и клиент не восстанавливался минутами.

После перезапуска egress начинает с мирового сервера, который перед этим
проработал хотя бы 2 минуты (запоминается в томе `egress-state`), а не с
`world-1.conf`; выбранный в «Шлюзе» сервер важнее. Если и он не отвечает,
egress перебирает серверы по порядку, по 30 секунд на каждый: так было
30.09, когда world-1 и world-2 принимали рукопожатие, но не пропускали данные,
и мир стоял 2,5 минуты.

`reflux status` показывает, сколько пакетов остановил kill switch: это
попытки выйти мимо туннелей. В нормальной работе там 0.

После обновления ядра убедитесь, что DKMS пересобрал модуль:
`grep amneziawg /proc/modules`. Без модуля egress не поднимет туннели и
трафик клиентов остановится (не утечёт).

## Резервные копии

В `~/reflux` всё, без чего клиентов не восстановить: ключи, документы, конфиги
AWG, настройки бота и сайта. Резервная копия — архив этого каталога раз в
день; копии **остаются на сервере**: ни бот, ни сайт их не выдают, они только
показывают в проверке, сколько времени прошло с последней.

```sh
reflux backup install          # раз в день в 04:30 в ~/reflux-backups, хранятся 14 последних
reflux backup install --dir /mnt/disk3/reflux-backups --keep 30   # другой диск, 30 копий
reflux backup                  # копия сейчас (например, перед большими изменениями)
reflux backup list             # копии, новые сверху
```

- Копия на том же диске спасает от ошибки (отозвали не того клиента, испортили
  настройку), но не от отказа диска; от него — `--dir` на другом диске.
- В копию не входят блокировки, сокеты нод, `heal.log`, история графиков сайта
  (`metrics.json`) и входы на сайт (`web-login.json`, `web-sessions.json`):
  старая копия не должна возвращать завершённые сеансы.
- Архивы доступны только владельцу (`0600`), каталог — `0700`. Внутри ключи
  и токен бота: не копируйте их туда, где их могут прочитать другие.
- Таймер — служба пользователя `reflux-backup.timer`; пропущенный из-за
  выключенного сервера запуск выполняется после включения. Если последней
  копии больше двух суток, проверка (`reflux doctor`, бот, сайт) предупреждает.

Восстановление:

```sh
reflux backup list
reflux restore reflux-20261001-043000.tar.gz
```

`restore` спрашивает подтверждение (`--yes` — без вопроса), сначала делает
копию текущего состояния (её можно вернуть так же), заменяет содержимое
`~/reflux` содержимым архива и пересоздаёт egress и все ноды. Если в копии
другие настройки бота или сайта, перезапустите их: `reflux bot install`,
`reflux web install`.

## Бот для клиентов и заявки на доступ

Второй, публичный бот: в нём люди просят доступ и получают всё, что нужно
приложению. Он работает в том же процессе, что и ваш бот (`reflux bot run`),
но умеет только заявки и выдачу человеку его собственного канала.

Настройка (один раз):

```sh
# в @BotFather: /newbot — второй бот, для клиентов
reflux bot client          # вставить его токен (хранится в ~/reflux/client-bot.json, 0600)
reflux bot install         # перезапустить бота: теперь работают оба
```

Дайте людям ссылку `https://t.me/<имя бота>`. `reflux bot client off`
отключает бота для клиентов.

**Скрыть от чужих.** Кнопка «🙈 Скрыть бота клиентов от чужих» в настройках
вашего бота (на сайте — вверху страницы «Заявки», в консоли — `reflux bot
client hide`, обратно — `show`) делает так, что бот для клиентов отвечает
только своим: тем, у кого есть канал, чья заявка ждёт или одобрена, и тем,
кто пришёл по приглашению (`reflux invite`). Остальным он не отвечает вообще,
ни на сообщения, ни на кнопки, и заявок от них не появляется. Сам бот в
Telegram при этом остаётся: его имя можно найти, он просто молчит.

Что видит человек (короткие экраны, у каждого одна главная зелёная кнопка):
- «📨 Запросить доступ» → может написать, кто он → «Заявка отправлена»; вам
  сразу приходит сообщение с кнопками. Пока ждёт — может отозвать заявку или
  уже скачать приложение («⬇️ Скачать ReFlux» — APK последнего релиза).
- После одобрения бот присылает «🎉 Доступ открыт», QR (для второго телефона)
  и ссылку: нажатие копирует её, а в ReFlux её добавляют через «Профили → QR →
  Вставить ссылку». QR и ссылка удаляются через 10 минут — профиль остаётся в
  приложении.
- Потом — его канал: работает ли и до какого числа (🟢, ⏸, 🔴), подключено ли
  приложение и трафик за месяц. Кто ещё ни разу не подключался, видит отсылку
  к инструкции. Кнопки: «⚡ Подключить» (QR и ссылка, не чаще раза в
  2 минуты), «📖 Инструкция», «🆘 Не работает», «⏳ Продлить» (за неделю до
  конца срока; когда срок вышел — вместо «Подключить»).
- «📖 Инструкция» — четыре шага (установить, получить ссылку, вставить,
  включить) и свёрнутый блок «Не получается?»: установка APK, старые
  телефоны, другие VPN.
- За 3 дня до конца доступа и когда он закончился бот напоминает сам.
- Отклонённым бот сообщает об отказе; попросить снова можно через сутки.
  Заблокированным — «Доступ закрыт».
- «🆘 Не работает»: человек пишет, что не так (или отправляет без описания), а
  вам приходит его текст и то, что сервер видит о канале: доступ, в сети ли и
  когда был, через какой документ идёт трафик, работают ли туннели. Не чаще
  раза в 10 минут.
- Язык — по настройке Telegram человека (английский для `en`, иначе русский).
- Свои слова в конце инструкции — в файле `~/reflux/client-help.txt` (обычный
  текст).

Каждая заявка — файл в `~/reflux/requests/`. Решать можно где удобно:

- **в вашем боте** — сообщение о заявке с кнопками «✅ 30 дней», «✅ 90 дней»,
  «✅ Бессрочно», «❌ Отклонить», «🚫 Заблокировать»; кнопка «📨 Заявки» на
  главном экране и команда `/requests`;
- **на сайте** — страница «Заявки» (в меню — число ожидающих);
- **в консоли**:

```sh
reflux requests                              # все заявки
reflux requests approve @ник --expires 90    # одобрить (+30 по умолчанию, never — бессрочно)
reflux requests reject @ник                  # отклонить (попросить снова можно через сутки)
reflux requests block @ник                   # заблокировать
reflux requests forget @ник                  # забыть: человек сможет попросить снова
```

Одобрение создаёт клиента: имя — ник Telegram (`dima_k` → `dima-k`, без ника —
`tg<id>`), документ — первый свободный из пула, клиент привязан к аккаунту
Telegram, в заметке — что человек написал. Нода запускается сразу, а бот для
клиентов присылает человеку ссылку и QR. Заявка «продлить» добавляет срок к
текущему доступу клиента.

С одного аккаунта — одна заявка; одобренная ждёт, пока бот для клиентов не
отправит ссылку. Ожидающих заявок не больше 20.

### Приглашения

Чтобы дать доступ без заявки, сделайте приглашение — одноразовую ссылку в бот
для клиентов: кто её откроет, сразу получит канал (клиент создаётся так же,
как при одобрении заявки) и QR, а вам придёт сообщение, кто пришёл.

- в вашем боте: «📨 Заявки» → «🎟 Пригласить» → срок (30, 90 дней, бессрочно),
  бот покажет ссылку; там же список действующих и «Отозвать»; команда `/invite`;
- на сайте: страница «Заявки», блок «Приглашения» (срок и заметка — кому);
- в консоли: `reflux invite --expires 90 --note Олег`, `reflux invite list`,
  `reflux invite revoke <код>`.

Приглашение можно сделать и для уже созданного клиента без аккаунта — ссылку
для человека: кто её откроет, будет привязан к этому клиенту (срок и
документы остаются те же) и сразу получит QR и ссылку. В вашем боте: карточка
клиента → «🔗 Telegram» → «🎟 Ссылка для человека» (кнопка есть и сразу после
«➕ Добавить»); в консоли: `reflux invite --client <имя>`.

Ссылка действует 7 дней и срабатывает один раз. Если по ней пришёл тот, кто
не может её использовать (заблокирован, уже есть канал или заявка), она не
сгорает. Если в пуле не осталось документов, вместо канала создаётся обычная
заявка — её решаете вы.

## Telegram-бот

Бот раз в минуту выполняет проверки `reflux doctor` и пишет в Telegram, когда
что-то меняется: упал или поднялся туннель, мировой туннель переключился на
другой сервер, нода не запущена или не подключена ни к одному своему документу,
умер документ, закончился срок доступа
клиента, обновился образ, заканчивается место на диске. Изменение должно
продержаться две проверки подряд: перезапуск ноды или короткий сбой туннеля не
будят. При запуске бот присылает сводку.

Бот отвечает только вашему аккаунту, остальных молча игнорирует. Управлять
можно кнопками: `/start` открывает главный экран, дальше всё в одном
сообщении, которое меняется при нажатии.

- **Главная** — туннели, kill switch и клиенты: 🟢 в сети, ⚪ не в сети,
  ⏸ пауза, ⌛ срок истёк, 🔴 нода не работает; рядом с именем — владелец из
  Telegram, если клиент привязан. Кнопки: обновить, проверка, клиенты,
  добавить, 🚀 скорость, настройки.
- **Проверка** — все проверки `reflux doctor`; там же «Перезапустить всё».
- **Клиент** — доступ, нода, в сети ли клиент, трафик, аккаунт Telegram.
  Кнопки: 📱 QR и ссылка, ⏸ пауза / ▶️ включить, 📅 срок доступа,
  🔗 Telegram, ✏️ переименовать, 📜 журнал, 🗑 отозвать.
- **📅 Срок доступа** — сколько осталось; +1, +7, +30, +90 дней и +1 год
  (от конца срока, пока он не истёк, иначе от текущего момента), ♾ бессрочно,
  ⛔ завершить сейчас (нода останавливается сразу), ✍️ ввести дату или срок
  (`2026-12-31`, `30d`, `never`).
- **🔗 Telegram** — привязать клиента к своему аккаунту, отвязать или
  получить «🎟 Ссылку для человека»: кто её откроет в боте для клиентов,
  будет привязан к клиенту и получит QR и ссылку. После привязки к себе бот
  предлагает назвать клиента вашим ником.
- **✏️ Переименовать** — бот просит новое имя. Ссылка и ключ не меняются,
  нода перезапускается (канал пропадает примерно на минуту). В консоли:
  `reflux rename <имя> <новое-имя>`.
- **🌐 Шлюз** — какой мировой сервер работает, ваш выбор и режим России;
  кнопки серверов переключают мир (✅ — используется, ⏳ — выбран, egress
  переходит за 10 секунд), «🔁 Автоматически» отменяет выбор; режим России
  (туннель + резерв, только туннель, напрямую) меняется после подтверждения
  с перезапуском egress и нод.
- **🚀 Скорость** — скачивание 50 МБ из России (Selectel, запасной —
  зеркало Яндекса) и из мира (Cloudflare, запасной — OVH) через egress, тем же
  путём, что трафик клиентов; в консоли `reflux speedtest`. Тестовые сервисы
  отвечают «429 Too Many Requests» адресу, который много скачивал, — тогда
  замер берёт следующий источник и пишет, откуда скачано. Это скорость выхода сервера: канал клиента через
  документ медленнее (около 10–20 Мбит/с).
- **📊 Сервер** — процессор, память, температура, время работы, трафик
  клиентов и домашней сети, диски и самые загруженные процессы (замер за
  секунду в момент нажатия).
- **🔁 Перезапустить ноду** — в карточке клиента.
- **➕ Добавить** — достаточно прислать имя (`guest`) или имя со сроком
  (`guest 30d`): основной и запасной документы бот возьмёт из пула. Свой
  документ — ссылкой после имени: `guest https://cloud.mail.ru/public/… 30d`.
  Клиент создаётся без аккаунта; отдать его человеку — кнопкой «🎟 Ссылка для
  человека» сразу или позже.
- **⚙️ Настройки** — язык: русский (по умолчанию) или английский (меняет
  экраны, уведомления и меню команд) и какие уведомления получать: туннели,
  клиенты и ноды, обновления (новые образы, запуск бота), сервер (модуль AWG,
  маршрутизация, Docker, cron, диск, температура, процессор). Выключенные
  группы бот не присылает, но `/doctor` и главная показывают всё. Там же пороги
  предупреждений о сервере (кнопки ±):
  - **температура процессора** — по умолчанию собственный предел датчика
    (у coretemp на этом сервере 82 °C), шаг 5 °C, от 60 до 100 °C. Предупреждение
    снимается, когда температура опустится на 5 °C ниже порога; проблема
    (`FAIL`) — за 5 °C до критической точки датчика (102 °C), где процессор
    замедляется;
  - **процессор занят** — на 90 % и больше 10 минут подряд (порог от 50 до
    100 % с шагом 10). В предупреждении — какой процесс занимает его больше всех
    (например, `qbittorrent-nox`). Это видит только бот: он замеряет процессор
    между проверками; `reflux doctor` показывает лишь температуру.

  Красная полоса на графике температуры на сайте проходит по тому же порогу.

**Еженедельный отчёт.** По понедельникам с 10:00 бот присылает итоги прошлой
недели (с понедельника по воскресенье): трафик каждого клиента и самый
загруженный день (считает сайт, `traffic.json`), сколько было проблем,
предупреждений и восстановлений, какую долю времени работали туннели, кто не
пользуется каналом две недели и дольше, у кого
в ближайшие две недели кончается доступ, заполненность диска `/` и время
работы сервера. Если в понедельник бот
не работал, отчёт придёт позже в ту же неделю. Выключается в «⚙️ Настройках»
(группа «Еженедельный отчёт»); `/report` — те же итоги за последние 7 дней в
любой момент.

**Обновления.** Раз в 6 часов бот спрашивает GitHub (GHCR), не вышли ли новые
образы ноды и egress, и один раз на каждую новую версию присылает «⬆️ Доступно
обновление» с кнопкой «Обновить сейчас» (как `reflux update`: egress и ноды
перезапустятся, каналы пропадут примерно на минуту). Экран «⬆️ Обновления» в
«📊 Сервер» показывает текущие версии, проверяет сразу и включает
**автообновление ночью**: тогда бот ставит новые образы сам между 4 и 5 часами
и сообщает об этом. Сбои, которые вызывает перезапуск, 5 минут после обновления
не присылаются (в журнал событий записываются).

**Конец доступа.** За 3 дня до окончания срока доступа клиента бот
предупреждает (группа «Клиенты и ноды») и подсказывает, как продлить; после
продления сообщает, что всё в порядке.

**Сообщение клиентам.** «👥 Клиенты» → «📣 Сообщение клиентам» → напишите текст
→ подтвердите: бот для клиентов отправит его всем активным клиентам,
привязанным к Telegram (например, перед перезагрузкой сервера), и скажет,
скольким дошло.

Те же действия есть командами (меню «/» у поля ввода): `/start`, `/doctor`,
`/clients`, `/add <имя> <ссылка> [срок]`, `/show <имя>`, `/pause`, `/resume`,
`/expire <имя> <срок>`, `/rename <имя> <новое-имя>`, `/revoke <имя>`,
`/restart`, `/logs <имя|egress>`, `/speedtest`, `/gateway`, `/report`, `/settings`.

Отзыв клиента и перезапуск выполняются только после кнопки подтверждения;
кнопка действует 10 минут.

`/show` присылает ключ клиента через Telegram: переписка с ботом не
зашифрована сквозным шифрованием. Оба сообщения бот удаляет через 10 минут
(если бот за это время перезапустится, удалите их сами).

Команды бота, `reflux` в консоли и `heal` из cron меняют клиентов по очереди
(блокировка `~/reflux/.lock`): `heal` пропускает минуту, остальные ждут до
двух минут.

Настройка (один раз, по SSH на сервере):

1. В Telegram откройте @BotFather, отправьте `/newbot`, придумайте имя.
2. `reflux bot setup` — вставьте токен, который дал BotFather, затем откройте
   ссылку на бота и нажмите «Start»; подтвердите свой аккаунт словом `yes`.
   Токен хранится в `~/reflux/telegram.json` (права 600), в репозиторий не
   попадает.
3. `reflux bot install` — запускает бота как пользовательскую службу systemd
   (`~/.config/systemd/user/reflux-bot.service`).
4. Один раз: `sudo loginctl enable-linger $USER` — иначе службы пользователя
   останавливаются, когда вы выходите из SSH.

Проверка: `reflux bot test` присылает тестовое сообщение;
`systemctl --user status reflux-bot` и `journalctl --user -u reflux-bot`.
После обновления утилиты `reflux` повторите `reflux bot install`: служба
перезапустится с новой версией.

Бот обращается к `api.telegram.org` с самого сервера, как `docker pull`, а не
через egress: иначе он не смог бы сообщить, что egress упал. Трафик клиентов
этим путём не идёт.

## Сайт в домашней сети

Те же экраны, что у бота, в браузере: главная (туннели и клиенты, обновляется
сама), клиент (QR и ссылка — по кнопке, пауза, срок, переименование, отзыв с
вводом имени, журнал, заметка), добавление клиента (см. ниже),
проверка, шлюз (мировой сервер, режим России, канал mail.ru), скорость.

Страницы:

- **Главная** — плитки (процессор, память, температура, трафик клиентов,
  диск `/`) с графиками за последний час, туннели, последние события и клиенты
  с текущей скоростью и трафиком за сегодня. Обновляется сама раз в 15 секунд.
- **Сервер** — панель в духе Grafana: сколько туннелей, клиентов и
  контейнеров работает и не работает; процессор, нагрузка 1/5/15 минут, память,
  температура, время работы; графики процессора (красная полоса — выше 80 %),
  нагрузки, трафика клиентов и домашней сети в Мбит/с, температуры и памяти за
  15 минут, час, 6 или 24 часа (переключатель вверху); индикаторы процессора,
  памяти, swap, температуры и диска `/`; все диски с заполнением, контейнеры
  ReFlux, самые загруженные процессы (например, qBittorrent) и датчики
  температуры. История дольше часа — средние по минутам за сутки, хранится в
  `~/reflux/metrics.json` и переживает перезапуск сайта; пока сайт не работал,
  на графиках разрыв.
- **События** — что сообщал бот: туннель упал или поднялся, переключение
  сервера, обновление образа, запуск бота (последние 200; хранятся в
  `~/reflux/events.jsonl` и записываются, даже если группа уведомлений в боте
  выключена).
- **Добавить клиента** — имя (подсказано свободное) и заметка: кто это или какое
  устройство (видна на главной, на странице клиента и в боте; меняется на
  странице клиента, `reflux add --note`). Документ — из пула (список свободных,
  сначала mail.ru) или по ссылке, тип по ссылке или выбранный; вписанная ссылка
  важнее выбора из пула. Резервные документы из пула (нода станет Session).
  Срок доступа кнопками (бессрочно, день, неделя, 30 и 90 дней, год) или до
  даты; «Запустить ноду сразу» — без отметки клиент добавится на паузе.
  Привязка к аккаунту Telegram, который бот уже знает. После добавления
  открывается страница клиента с кнопкой QR.
- **Клиент** — плюс учёт трафика: сегодня, за месяц и всего (до 70 дней),
  столбцы трафика по дням за 30 дней (при наведении — цифры за день), график
  скорости за последний час в Мбит/с и кнопка «Перезапустить ноду».
- **Шлюз** — плюс туннели AWG (когда было последнее рукопожатие и сколько
  прошло трафика) и доступность туннелей за 14 дней: какую долю времени
  работали мир и Россия (бот проверяет каждую минуту и записывает в
  `~/reflux/uptime.json`; Россия через резерв напрямую считается работающей,
  остановленный egress — простоем обоих).

Учёт трафика ведёт сайт, пока он работает: раз в 10 секунд он читает счётчики
нод и складывает прибавку по дням в `~/reflux/state/<имя>/traffic.json`.
Перезапуск ноды (её счётчики начинаются с нуля) и перезапуск самого сайта учёт
не сбивают.

Установка (один раз):

```sh
reflux web install --listen 192.168.1.201:8686 --trust 192.168.1.124,192.168.1.140
sudo ufw allow from 192.168.1.0/24 to any port 8686 proto tcp
```

- Сайт слушает только домашний адрес сервера и отвечает только адресам
  локальной сети; через VPN сервера и сети Docker он не виден.
- Вход без пароля: команда `/web` в боте или `reflux web login` на сервере
  дают одноразовую ссылку на 10 минут; браузер после неё помнит вход 30 дней
  («Выйти» завершает). На диске хранятся только хеши ссылок и сеансов
  (`~/reflux/web-login.json`, `web-sessions.json`).
- Адреса из `--trust` входят сразу, без ссылки. Кто займёт такой адрес, тоже
  войдёт, поэтому закрепите их за своими устройствами на роутере (резервирование
  DHCP).
- Изменения принимаются только со страниц самого сайта (проверка Origin,
  cookie `SameSite=Strict`); ключ клиента показывается только по кнопке и не
  сохраняется в истории и кеше браузера.
- Служба пользователя `reflux-web`, как бот: после обновления `reflux` я
  перезапускаю её `reflux web install` (параметры берутся из `~/reflux/web.json`).

## Проверка, что всё идёт через туннели

```sh
docker exec reflux-egress wget -qO- https://api.ipify.org   # IP текущего мирового сервера
docker exec reflux-egress ip route get 77.88.8.8            # ... dev awg-ru: Россия в российский туннель
docker exec reflux-egress ip route get 9.9.9.9              # ... dev awg-world: остальное в мировой
```

IP сервера (`curl https://api.ipify.org` на самом хосте) не должен совпадать с
тем, что видит egress.
